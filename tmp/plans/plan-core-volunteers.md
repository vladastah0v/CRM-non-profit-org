# План: каркас + ядро + модуль «Волонтёры» (CRM НКО)

Источник: «ТЗ: внутренняя CRM для учёта волонтёров и подопечных НКО» от 05.10.2026.
Объём этой работы: этапы 2, 3, 4 из раздела 8 ТЗ. После каждого этапа — стоп, отчёт, твой коммит.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Объём | Каркас (этап 2) → Ядро (этап 3) → «Волонтёры» (этап 4). Остальное — после |
| Окружение | Docker Desktop: всё через `docker compose` |
| Стили | Tailwind CSS v4, standalone CLI (без Node.js), сборка в Docker |
| CI | GitHub Actions: ruff, mypy, pytest + сборка образа |
| Часовой пояс | Europe/Moscow (переменная `TIME_ZONE`) |
| 2FA | django-otp (TOTP) |
| Git | `git init` + `.gitignore`, без коммитов — коммитишь ты |
| Python | 3.12 в Docker-образе (по ТЗ); локальный 3.14 — только для `py_compile` |
| Django | 5.2 LTS |

## Этап A — Каркас и инфраструктура (ТЗ этап 2)

1. `git init`, `.gitignore`, `.editorconfig`, `pre-commit` (ruff, mypy).
2. Django-проект, настройки через переменные окружения (`django-environ`), `.env.example`.
3. Dockerfile (python:3.12-slim, сборка Tailwind отдельной стадией), docker-compose:
   web, PostgreSQL 16 (pg_trgm, citext), Redis 7, Celery worker, Celery Beat, Nginx.
   ~~MinIO~~ — убран (изменение, ждёт подтверждения): файлы шифруются на уровне приложения
   и выдаются только через Django; в разработке — локальный диск, на сервере — S3 в РФ.
4. `docker-compose.prod.yml`: Gunicorn, Nginx с TLS/HSTS, без MinIO (S3 в РФ из переменных).
5. GitHub Actions: ruff → mypy → pytest (с сервисом PostgreSQL) → сборка образа.
6. Базовый шаблон: меню, навигация, адаптивная сетка от 360 px, русский язык, ДД.ММ.ГГГГ.
7. Подключение GlitchTip/Sentry через `SENTRY_DSN` (необязательно), healthcheck-эндпоинт.
8. README: запуск локально за 15 минут.

**Проверка:** `docker compose up` поднимает все сервисы; главная страница открывается;
`ruff`, `mypy`, `pytest` проходят; `manage.py check --deploy` с prod-настройками без критичных замечаний.

## Этап B — Ядро (ТЗ этап 3)

1. Пользователь (логин, ФИО, роли M:N, активен), 5 ролей из раздела 2.1, права суммируются.
2. Вход: пароль → TOTP. Подключение телефона — только с одноразовым кодом от администратора
   (добавлено по итогам ревью безопасности: иначе знающий пароль мог привязать своё устройство).
   Пароль ≥ 12 символов, Argon2; блокировка на 15 мин после 5 неудачных попыток;
   выход после 30 мин бездействия.
3. Механизм прав на уровне объекта: менеджеры `visible_to(user)` + политика по матрице 2.2;
   ограниченный набор полей («О») — на уровне выборки и шаблона.
4. Журнал аудита: вход/выход, неудачный вход, просмотр чувствительных карточек, выгрузки,
   изменения прав. Запрет UPDATE/DELETE триггером PostgreSQL. История изменений — django-simple-history.
5. Шифрованное поле (AES-GCM, `cryptography`), ключи в переменных окружения, поддержка ротации.
6. Справочники в админ-панели (Django Admin + Unfold): навыки, программы, типы помощи,
   категории подопечных, причины выбытия, районы, типы обучения.
7. Файлы: S3 (django-storages), проверка типа и размера ≤ 20 МБ, подписанные ссылки с ограниченным сроком.
8. Блокировка пользователя администратором (ФТ-А-01), просмотр журнала аудита с фильтрами (ФТ-А-03).

**Результат по ТЗ:** ФТ-А-01…03, НФТ-ИБ-02…07, НФТ-ИБ-11.
**Проверка:** тесты на вход без 2FA, блокировку после 5 попыток, тайм-аут, неизменяемость аудита,
шифрование/расшифровку и ротацию ключа, подписанные ссылки, права по каждой роли.

## Этап C — Модуль «Волонтёры» (ТЗ этап 4)

1. Модели: волонтёр, навыки (M:N), программы (M:N), доступность, обучение, ручные часы,
   журнал смены статусов (для будущей воронки ФТ-О-03), данные законного представителя.
2. Список с фильтрами (статус, навыки, район, доступность, программа), поиск, пагинация,
   сортировка, сохранение фильтров; карточка волонтёра; HTMX.
3. Статусы с проверкой переходов в сервисном слое (раздел 4.3): «активен» — только при
   действующем согласии и пройденном обучении; «выбыл» — причина из справочника.
4. Проверка дублей: телефон, email, ФИО + дата рождения (pg_trgm, нормализация телефона).
5. API приёма анкет `/api/v1/intake/volunteer/`: HMAC-SHA256, 10 запросов/мин с IP,
   фиксация согласия, проверка дублей, уведомление координаторам.
6. Согласия волонтёров (ФТ-Д-01): тип, дата, подписант, скан, срок, отзыв.
7. Несовершеннолетние (ФТ-В-08): обязательные данные представителя и его согласие.
8. Уведомления координаторам в интерфейсе (колокольчик) — ФТ-У-02.

**Результат по ТЗ:** ФТ-В-01…08, ФТ-Д-01, ФТ-У-02, п. 7.1 (для волонтёров).
**Проверка:** тесты всех переходов статусов, дублей, HMAC, лимита запросов, прав
(куратор видит ограниченные поля, аналитик — ничего), покрытие бизнес-логики ≥ 70 %.

## Допущения — подтверди или поправь

1. Куратор видит в карточке волонтёра («Ч (О)»): ФИО, телефон, Telegram, район, навыки, статус.
2. Статус «выбыл» — конечный (вернуть волонтёра можно только новой анкетой).
3. При найденном дубле интерфейс показывает совпадения и даёт сохранить только после подтверждения;
   анкета с сайта создаётся всегда, но с пометкой «возможный дубль».
4. Уведомления в MVP — внутри интерфейса; email/Telegram сотрудникам — позже.
5. Сохранённые фильтры списков хранятся в профиле пользователя (не теряются после выхода).
6. Анкета с сайта: подпись `X-Signature: sha256=<hex>` от тела запроса + `X-Timestamp`
   (окно 5 минут против повторной отправки).
