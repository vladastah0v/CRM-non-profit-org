# Правила разработки

## Архитектура

Монолит на Django с серверным рендерингом (раздел 6 ТЗ). Telegram-бот — отдельный
процесс, к базе не обращается, ходит только во внутренний API.

```
 Сотрудники ──HTTPS──> Nginx ──> Django (Gunicorn) ──> PostgreSQL
 Сайт фонда ──HMAC───>   │              │         └──> Redis <── Celery + Beat
                          │              └──> файлы (зашифрованы, вне веб-корня)
 Волонтёры ──Telegram──> бот ──внутренний API (токен)──> Django
```

## Слои внутри приложения

| Файл | Что в нём | Чего в нём нет |
|---|---|---|
| `models.py` | поля, ограничения БД, менеджеры `visible_to(user)` | бизнес-правил переходов |
| `services.py` | все изменения: создание, переходы статусов, проверки | работы с request |
| `selectors.py` | выборки для списков и карточек, только через `visible_to` | изменений |
| `views.py` / `api.py` | разбор запроса, вызов сервисов и выборок | бизнес-логики |

Веб-интерфейс, API и бот вызывают **одни и те же** сервисы — правила действуют одинаково.

## Обязательные правила

- Первичный ключ — UUID; в каждой таблице `created_at/updated_at/created_by/updated_by`.
- Записи не удаляются, а архивируются (`is_archived`). Физическое удаление — только обезличивание.
- Любой список и любая карточка строятся через `Model.objects.visible_to(user)`.
  Прямой `Model.objects.get(pk=...)` во view запрещён — это IDOR (НФТ-ИБ-08).
- Справочники — таблицы в БД, не перечисления в коде.
- Деньги — `DecimalField(max_digits=12, decimal_places=2)`; дата и время — с часовым поясом.
- Секреты — только в переменных окружения.
- ПДн не пишутся в логи и не уходят во внешние сервисы.
- Код требования ТЗ (`ФТ-В-02`) указывается в docstring сервиса и в названии теста.

## Доступ и роли

- Роли — `apps/accounts/roles.py` (`RoleCode`). Проверка: `user_has_role(user, RoleCode.ADMIN)`.
  Права нескольких ролей суммируются; суперпользователь считается администратором.
- Веб-интерфейс — только сотрудники (admin, coordinator, curator, analyst) после 2FA.
  `RequireOTPMiddleware` не пускает дальше страницы ввода кода.
- Права на объекты — в `QuerySet.visible_to(user)` модели, по матрице 2.2 ТЗ.
  В view: `get_object_or_404(Model.objects.visible_to(request.user), pk=pk)`.
- Админ-панель — только роль «Администратор». Наследуйте классы от `CRMModelAdmin`:
  удаление выключено, есть действия «в архив / из архива», изменения пишутся в аудит.

## Журнал аудита

- `apps.audit.services.log_event(AuditAction.X, request=..., obj=..., fields=[...])`.
- В журнал не пишутся значения полей и ФИО — только тип и id объекта, названия полей.
- Изменить запись нельзя ни через ORM, ни SQL-запросом (триггер PostgreSQL);
  удалить — только старше 1 года. Поэтому `manage.py flush` в рабочей базе не работает.

## Шифрование и файлы

- Чувствительные поля — `apps.core.fields.EncryptedTextField` (AES-256-GCM).
  Поиск и сортировка по ним невозможны — шифруйте только то, что действительно чувствительно.
- Ключи — `FIELD_ENCRYPTION_KEYS="новый:ключ,старый:ключ"`. Ротация:
  `generate_encryption_key` → новый ключ первым в списке → перезапуск →
  `rotate_encryption_keys` → старый ключ убрать.
- Файлы — только через `apps.consents.files.store_attachment()`: проверка типа по
  содержимому, до 20 МБ, шифрование. Ссылка на скачивание — `make_download_url()`,
  живёт 5 минут и только для одного пользователя.

## Статусы и проверки

- Переходы статусов — таблица `TRANSITIONS` и функция `change_status()` в `services.py`
  модуля. Поле `status` в модели `editable=False`: формы и админка его не меняют.
- Каждая смена статуса пишется в журнал статусов модуля (`VolunteerStatusChange`) —
  из него строится воронка (ФТ-О-03) — и в журнал аудита.
- Ошибки правил — `ValidationError` с понятным текстом на русском; в view их переносит
  в форму `apply_service_errors()`.

## Согласия и чувствительные данные

- Согласие относится ровно к одной карточке (`volunteer` или `beneficiary`) — это проверяет
  ограничение в базе. Создание — `apps.consents.services.create_consent()`.
- За несовершеннолетнего действующим считается только согласие законного представителя.
- Подопечный: в «В работе» — только с действующим согласием и куратором; карточку в работе
  без согласия сохранить нельзя (ФТ-Д-02); отзыв последнего согласия переводит случай на паузу.
- Здоровье и инвалидность сохраняются только при согласии на особые категории (НФТ-ПД-03).
- Защищённый блок — отдельная страница: каждое открытие пишется в аудит (`VIEW_SENSITIVE`),
  в ленте истории — только названия изменённых полей, без значений.
- Проверка дублей — `apps.core.duplicates.find_person_duplicates()`; совпадения с карточками,
  к которым у пользователя нет доступа, показываются без ФИО и даты рождения.

## Списки

- Фильтры — `django-filter` (`filters.py`), выборка — `selectors.py` через `visible_to`.
- Сохранение фильтров — `apps.core.list_filters.restore_or_save()`: сохраняются только
  структурные параметры, текст поиска — нет (в нём бывают ФИО и телефоны).
- HTMX обновляет только блок результатов; адрес страницы меняется (`hx-push-url`), поэтому
  ссылку на отфильтрованный список можно скопировать. View отвечает фрагментом только на
  HTMX-запрос и полной страницей при возврате «Назад» (`Vary: HX-Request`).

## Заявки, помощь, взаимодействия

- Модель заявки — `HelpRequest` (не `Request`): в коде повсюду переменная `request` — HTTP-запрос.
- Заявка «выполнена» — только при хотя бы одном факте помощи; последний факт помощи
  выполненной заявки в архив не переводится.
- Помощь: количество или сумма (оба ≥ 0), ровно один исполнитель — сотрудник или волонтёр.
  Эти правила продублированы `CHECK`-ограничениями в базе.
- Взаимодействия и задачи привязаны к карточке двумя FK (`volunteer` / `beneficiary`),
  ровно один заполнен. Пишут их те, кто работает с карточкой; правит запись только автор.
- Исполнитель задачи выбирается из `assignees_for(card)` — только те, кто видит карточку.
- Периодические задачи — `apps/*/tasks.py` + `CELERY_BEAT_SCHEDULE` в `config/settings/base.py`.
  Они идемпотентны: отметка `reminded_on` / `deadline_notified_on` не даёт напомнить дважды.

## Уведомления

- `apps.notifications.services.notify(users, kind, title, url=...)`. В заголовке и тексте —
  без ФИО и контактов, только ссылка на карточку.
- Счётчик в шапке считается при загрузке страницы. **Не делайте периодический опрос
  сервера**: фоновые запросы продлевают сессию и отменяют выход по бездействию (НФТ-ИБ-04).

## Фронтенд

- Alpine.js — CSP-сборка: выражения в разметке не вычисляются, компоненты регистрируются
  в `static/js/app.js` через `Alpine.data(...)`.
- Встроенные `<script>` и `style="..."` запрещены политикой CSP.
- HTMX-запросы получают CSRF-токен автоматически из `<meta name="csrf-token">`.
- Все экраны проверяются на ширине 360 px.
