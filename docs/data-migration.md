# Перенос данных из таблиц (этап 9)

Для администратора фонда и разработчика. Итог этапа: данные перенесены, старые таблицы —
только для чтения (этап 10). Инструмент — импорт CRM (главная → «Импорт данных»).

## 0. До переноса

- **Согласия.** Переносить можно только людей, у кого есть основание обработки (риск
  п. 11.1 ТЗ). Составьте список, у кого согласия нет, и проведите кампанию по переподписанию.
  Без согласия подопечного случай в CRM нельзя перевести «в работу».
- **Состав полей** (НФТ-ПД-04): переносится только то, что есть в шаблонах. Диагнозы,
  паспорта, СНИЛС импортом не переносятся — их куратор вносит вручную в защищённый блок,
  при согласии на особые категории.
- **Справочники** заполняются в админ-панели до импорта: районы, навыки, программы, типы
  помощи, категории, источники, типы обучения, причины выбытия. Значения в файлах должны
  совпадать с названиями справочников (регистр не важен).
- **Сотрудники** заведены, у кураторов известны логины — они нужны в колонке «Куратор».

## 1. Очистка таблиц

1. Скачайте шаблоны (волонтёры, подопечные, история помощи) и перенесите данные в них.
2. Одна строка — один человек; ФИО — в три колонки; даты — ДД.ММ.ГГГГ.
3. Телефоны — в любом формате, CRM приведёт к +7…; явные дубли (один человек в двух
   строках) лучше объединить заранее — CRM сама найдёт совпадения по телефону, email,
   ФИО и дате рождения, но решение по каждому придётся принять вручную.
4. Статусы: волонтёру «Активен» — только при заполненных дате согласия и обучении; подопечному
   «В работе» — при дате согласия и кураторе. Иначе строка попадёт в ошибки.

## 2. Пробный импорт (тестовое окружение)

На тестовом сервере с копией справочников, в порядке: **волонтёры → подопечные → помощь**
(история помощи ищет подопечного по ФИО и дате рождения).

1. Загрузите файл — CRM покажет: сколько создать, обновить, ошибки по строкам, дубли.
   В базу на этом шаге ничего не попадает.
2. Скачайте отчёт об ошибках, исправьте строки в файле, загрузите снова. Повторяйте, пока
   ошибок нет или остались только осознанные.
3. «Импортировать». Повторная загрузка того же файла безопасна: совпавшие карточки
   обновятся, повторные факты помощи будут пропущены.

## 3. Проверка сотрудниками

- Координатор: 20 случайных волонтёров — статусы, навыки, районы, часы.
- Кураторы: свои подопечные — все ли на месте, верный ли куратор, согласия.
- Аналитик: отчёт по программе за прошлый квартал против ручного расчёта (сценарий 9.2,
  правила — [reports.md](reports.md)).
- Администратор: пометки «возможный дубль» — разобрать каждую.

Замечания — в файлы, исправления — в файлы, затем повторный пробный импорт на чистой
тестовой базе.

## 4. Финальный импорт (рабочий сервер)

1. Объявить сотрудникам «окно»: с этого момента старые таблицы не меняются.
2. Внеочередная резервная копия: `docker compose -f docker-compose.yml -f docker-compose.prod.yml exec backup crm-backup now`.
3. Импорт в том же порядке теми же файлами. Отчёты об ошибках — сохранить в протокол.
4. Выборочная проверка (как в шаге 3, в меньшем объёме).
5. Старые таблицы — в режим «только чтение» (права доступа в облаке/на диске), отметка
   «перенесено в CRM <дата>». Файлы импорта — удалить с компьютеров (в них ПДн).

## Если что-то пошло не так

Импорт создаёт обычные записи — ошибочные можно перевести в архив. Массовую ошибку
откатывает восстановление на момент до импорта ([deploy.md](deploy.md), «Восстановление»).
